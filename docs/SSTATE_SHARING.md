# Sharing sstate between builds

Why two builds that point at the same `SSTATE_DIR`, on the same layer pins, can
still rebuild almost everything — and how to tell, measure and fix it.

## TL;DR

| Check | Why it matters |
|---|---|
| Same `SSTATE_DIR` | Necessary, not sufficient. |
| Same **hash-equivalence DB** (`BB_HASHSERVE_DB_DIR`) | Sstate objects are looked up by *unihash*. Each DB hands out its own unihashes, so two DBs over one `SSTATE_DIR` make identical tasks diverge from the bottom of the dependency chain. |
| `build/cache/bb_unihashes.dat` | bitbake's local unihash cache is consulted **before** the server. Changing the DB path has no effect until this file is removed. |
| Same `MACHINE` / tune | Target recipes can only be shared between builds for the same package architecture. Across different machines, only native, cross, `allarch` and SDK objects can be shared. |
| Same layer pins **and** the same native-recipe appends | A `.bbappend` that touches a native recipe (`BBCLASSEXTEND = "native"`) changes its signature and everything built on top of it, up to `do_package` of every recipe. |
| `KAS_REPO_REF_DIR` | Shares layer **git objects** only. It has no effect on sstate. The reference mirrors also have to be refreshed (`git fetch`) or each build fetches recent history on its own. |

## How bitbake decides an object is reusable

1. Each task gets a **taskhash** from its inputs (variables, files, and the
   **unihashes** of the tasks it depends on).
2. With hash equivalence (`BB_SIGNATURE_HANDLER = "OEEquivHash"`, the default),
   the taskhash is mapped to a **unihash** by the hash-equivalence server. Tasks
   whose output turns out identical get the same unihash, so a change that does
   not alter output stops propagating.
3. Sstate objects are named, and looked up, by unihash.

Step 1 feeds dependency *unihashes* into the next taskhash. So if two DBs give
the same root task different unihashes, every task above it gets a different
taskhash. That happens even though the two builds have identical inputs, so
nothing above the root can be shared.

## Diagnosing a divergence

Find the first task whose signatures differ between two build trees. A plain
`bitbake-diffsigs` needs a configured environment. `scripts/sstate/sigtool.py`
calls the bitbake library directly (default `.kas/bitbake/lib`, override with
`--bitbake-lib`), so it works on any two `sigdata` files and does not touch a
running build:

```bash
# write current signatures without running anything
bitbake -S none <recipe>

# compare two sigdata files
scripts/sstate/sigtool.py walk <sigA> <sigB>

# ...and recurse into each dependency whose hash changed, down to the root
scripts/sstate/sigtool.py walk <sigA> <sigB> \
    --stamps-a <treeA>/tmp/stamps --stamps-b <treeB>/tmp/stamps

# raw field-by-field diff, when the summary hides which value differs
scripts/sstate/sigtool.py sigdiff <sigA> <sigB>
```

Interpret the deepest difference:

| Deepest difference | Cause |
|---|---|
| Only `unihash` differs, all inputs equal | Separate hash-equivalence DBs (or a stale `bb_unihashes.dat`). |
| A variable value differs | Real configuration difference (distro, machine, an append). |
| A file checksum differs | Different patch or source file. |
| `[export]` / `[func]` flags in one dependency list only | The sigdata files came from different bitbake versions; compare signatures generated by the same bitbake. |

Stamps and sstate `.siginfo` files are named by unihash, not taskhash. An old
`.siginfo` reached through hash equivalence describes the build that first
produced the object, possibly with older tools. For a like-for-like comparison,
generate fresh signatures with `bitbake -S none` in both trees.

Comparing the DBs themselves (opened read-only, safe while a build runs) shows
how far they disagree: for every `(method, taskhash)` present in both
`unihashes_v3` tables, do they record the same unihash? It also counts the
identical task outputs (`outhashes_v2`) that both have recorded.

```bash
scripts/sstate/sigtool.py dbcompare <dbA>/hashserv.db <dbB>/hashserv.db
```

## Measuring before you change anything

Always measure with a dry run and read the `Sstate summary` and the task
summary. What to compare is the **number of tasks left to run**, not the match
percentage:

```bash
bitbake -n <image>
#   Sstate summary: Wanted W Local L Mirrors 0 Missed M Current C (x% match, y% complete)
#   Tasks Summary: Attempted A tasks of which N didn't need to be rerun
#   tasks left to run = A - N
```

`bitbake -n` updates the mtime of every sstate object it checks. That does not
matter for building, but it defeats any later age-based pruning of the cache.

## Measured example (one image)

Two builds share one `SSTATE_DIR` and the same oe-core/bitbake pins, but use
different machines and separate hash-equivalence DBs.

| Configuration | Sstate wanted | Found in cache | Already current | Tasks left |
|---|---|---|---|---|
| Own DB (as built) | 2963 | 38 (1%) | 2386 | **5289** |
| Shared DB, local unihash cache kept | 2963 | 38 (1%) | 2386 | **5289** (no effect) |
| Shared DB, `bb_unihashes.dat` cleared | 4494 | 830 (18%) | 855 | **7260** |

DB comparison: of the 1292 taskhashes present in both DBs, 453 (35%) map to
different unihashes. The deepest signature difference for a simple native task
(`quilt-native:do_recipe_qa`) was the unihash alone, with identical inputs.

What it means:

- Sharing the DB does unlock the other build's objects: 22× more found in the
  cache here, mostly native and cross tools.
- Switching an *existing* build to a different DB throws away the work already
  recorded under the old one; in the measurement above that cost about 2000
  extra tasks.
- **Pick one DB path for every build on a shared `SSTATE_DIR` from the start**,
  or switch when a layer-pin move makes everything rebuild anyway.
- Running two builds at the same time against one SQLite DB with
  `BB_HASHSERVE = "auto"` starts two local servers on the same file. Avoid
  concurrent builds, or run one shared `bitbake-hashserv` and point
  `BB_HASHSERVE` at it.
